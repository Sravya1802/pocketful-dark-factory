# Pocketful stage 1 — ambiguity notes

Dark run: no questions asked. Where the requirements were unclear I chose the reading most consistent with the rest and wrote it here.
`Strict` = the check fails a service that reads it differently. `Lenient` = the check accepts either reading (so it cannot cause a false failure).

| # | Question | Choice and reason | Strict / lenient | Checks |
|---|---|---|---|---|
| A-01 | Missing/wrong-type field codes. §5 says wrong JSON type → 400, missing / bad value → 422, but amount, note, visibility strings/booleans/null are explicitly 422. | Handle/list/email/password fields of the wrong type (`to_handle: 7`, `participant_handles: "bob"`, `email: 5`) → **400 malformed_request**. `amount`/`note`/`visibility` of any wrong type listed in §5 → 422. `amount` as null/array/object is not listed → 400 **or** 422. | Strict for the listed cases; lenient for amount null/array/object | PAY-14 PAY-06 PAY-07 REQ-03 SPL-09 AUT-08 MDL-03 |
| A-02 | Settlement "malformed batch shape is 422" while §5 says wrong type is 400. | The settlement sentence is endpoint-specific and wins: `transfers` missing / not an array / entries not objects / handle fields missing → 422 `validation_failed`. A body that does not parse at all is still 400. | Strict | SET-11 SET-12 |
| A-03 | Signup with an email that is registered *and* whose handle is therefore also taken. | `email_taken` wins (the more specific, and it is the same account). | Strict | AUT-05 |
| A-04 | Is a third party (neither requester nor payer) acting on a request 403 or 404? §5: 403 = "not permitted to touch this resource", 404 = "not visible to this caller". | The requester/payer swap cases are 403 (spec text). A complete stranger or an operator: **403 or 404**. | Lenient | REQ-10 REQ-14 SET-18 |
| A-05 | Status for unrelated user vs. checks order on `pay`: permission vs. `request_not_pending` vs. visibility validation. | Not asserted except where the spec orders them (§7 key before everything). Wrong party is exercised only on a pending request. | n/a | REQ-10 |
| A-06 | Order of 401 vs 400 `missing_idempotency_key` when a request has neither token nor key. | 401 first (authentication precedes everything per §7: "…and the caller is authenticated"). Checks send a valid key with bad tokens and a valid token with bad keys, never both bad. | Strict only on the separated cases | ERR-02 IDM-01 |
| A-07 | For settlements: permission (403) vs. missing key (400) vs. validation. | 401 → 403 → 400 (key) → body. A non-operator with an invalid body gets 403. Operator without key and valid body gets 400. | Strict on SET-03 | SET-03 |
| A-08 | `note` "longer than 200 characters": characters = Unicode code points (200 emoji ok, 201 not). | Code points, not UTF-16 units or bytes; "200 emoji" is also a shipped check. | Strict | PAY-04 |
| A-09 | Unknown handle lookups are case-sensitive: `to_handle: "BOB"`. | Handles match `^[a-z0-9_]{1,20}$`, so no user has `BOB` → 404. Malformed handles (empty, 30 chars, trailing space) → 404 **or** 422. | Strict for `BOB`; lenient otherwise | PAY-13 |
| A-10 | Same key, "same JSON value": do `1000` and `1000.0` count as the same body? | Not asserted (Python-equal, JSON-text-different; implementations legitimately differ). Only key order and whitespace are asserted as irrelevant, and added/changed fields as different. | n/a | IDM-04 IDM-05 |
| A-11 | Unknown field added on replay (`{"to_handle":"bob","amount":100,"zzz":1}` under a key first used without it) | Different JSON value ⇒ 409 `idempotency_key_reuse` (§7 literally says same JSON value). Conflicts mildly with "unknown fields are ignored", but §7 is the specific rule. | Strict | IDM-05 |
| A-12 | Paying a request whose amount is 0 (possible only via splits). | Unspecified: payment amount must be ≥ 1 yet the request exists. Never exercised; split paid-in-full checks skip zero-amount requests. | n/a | SPL-12 |
| A-13 | `GET /requests` and `/activity` ordering inside one second. | Spec: unspecified for the feed; for requests "newest first by created_at". Checks space creations ≥1.1 s apart and assert order only then. Same-second ties are never asserted. | Strict across seconds only | REQ-17 FED-06 |
| A-14 | Timestamp offset forms. | `Z` and `+00:00`/`+02:00` forms both accepted ("explicit offset"); fractional seconds optional; must be within 10 min of the checker's clock. | Lenient | CNV-01.. |
| A-15 | `settlement_id` on non-settlement payments. | §11: "nonmembers expose null for that field" ⇒ the key is present with null in feed items. `POST /payments` / pay responses (shaped "exactly as" §8) may omit it or send null. | Strict in feed; lenient in `POST /payments` | FED-10 SET-06 |
| A-16 | Pay with no body at all. | Not exercised (checks always send `{}` or a body) — the spec shows a body-carrying call and the replay rules compare bodies. Decline/cancel are exercised both with no body and with `{}`. | n/a | REQ-12 REQ-13 |
| A-17 | Does the settlement `committed_at`/member `created_at` need to be near wall-clock? | Yes, within 10 minutes of the checker (a generous bound for clock skew). | Lenient | SET-16 |
| A-18 | Opaque export state: is `{}` an invalid state? | Not asserted. Asserted-invalid: `null`, string, number, boolean, arrays. A structurally damaged real state (one member replaced by a string) must be either rejected 422 with no change **or** accepted whole; never a 5xx and never half-applied. | Lenient | EXP-08 EXP-10 |
| A-19 | Concurrent pay of one request by distinct keys: which loser code? | `request_not_pending` (the request is no longer pending; insufficient funds can't apply since the payer is funded). | Strict | CON-04 CON-13 |
| A-20 | Signup race of different emails with the same derived handle. | Exactly one 201; the rest 409 `handle_taken`. | Strict | AUT-13 |
| A-21 | Request amount 0 via split vs. the "amount ≥ 1" rule on `POST /requests`. | §8 split text overrides: 0-amount requests from splits are legal; `POST /requests` with 0 is 422. | Strict | SPL-07 REQ-03 |
| A-22 | "Replay returns the original response … including after the resource changes": what if the replay's token is a different token of the same user? | Same user (any token) ⇒ same key scope. Not exercised by a dedicated check beyond IDM-07. | n/a | — |
| A-23 | `limit=007` or `limit=+4`/`limit= 4`. | "plain decimal digits": `+4`, `4.0`, `1e1`, empty, non-ASCII digits are 422. Leading zeros are not asserted either way. | Strict except zeros | REQ-18 FED-08 |
| A-24 | Deployment checks (§2) are not HTTP-observable. | Delivered separately as `docker_run_checks.sh` (needs docker). `run_checks.py` covers only HTTP. | — | DOC-01..05 |
