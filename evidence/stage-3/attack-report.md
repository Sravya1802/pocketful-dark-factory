# Pocketful stage 3 - attack report (adversary)

Revision attacked: `959960ce6bbf1afbc66caf6c59cc7ffeeaa89aaf` (`git archive` of `stage-3/`, product code untouched and not read).
Two containers (A :18300, B :18301, `--cpus 2 --memory 2g`, built with `DOCKER_BUILDKIT=0` and an empty `DOCKER_CONFIG`) for cross-process import, one `--network none` container (health 200), plus the frozen stage-1 (621342c) and stage-2 (92bbbf9) services as host node processes for real exports. Scripts and recorded output are in `evidence/stage-3/attacks/`:
`oracle3.py` (my own independent model, written from the spec: selected revisions by `known_at`, effective-time ordering, holds as events, correction outcome prediction incl. precedence and the historical-overdraft boundary check), `fuzz3.py` (random-sequence fuzz against the oracle), `attack_s3.py` (targeted attacks, 503 checks), `scale_snapshots.py`, `snapshot_growth.py`, `seeded_expired_hold.py`, regression copies `attack_s2_api_on_s3.py` and `ui_attack_s3_regress.py`, outputs `run-*.txt`.
Not used: the analyst's oracle/checks, the shipped harness.

## Verdict
The core ledger is correct: **0 mismatches against my oracle in 94 000 comparisons** (16 seeds x ~110 random operations, 505 successful corrections, 70 `historical_overdraft` and 69 `insufficient_funds` outcomes all predicted correctly) and every targeted race, precedence, idempotency, import and round-trip attack passed. Findings below are one memory-growth defect that can crash the service, one inconsistent historical view for a seeded edge case, and one RFC 3339 parsing gap.

## Findings (reproduced)

### S3-1 - Statement snapshots retain O(history) memory per snapshot once any write happened since the previous read; the service dies with a heap OOM - Medium
- Spec: "Statement/snapshot memory must stay bounded (snapshots live until reset)"; §2 2 GiB.
- Expected: snapshot cost small or shared (a frozen view must not copy the whole history each time).
- Actual: read-only repetition is flat (1900 snapshots of an 8000-payment statement: 42 MB), but **after any write between reads** (a payment or a successful correction) every new snapshot adds ~137 bytes x history length. 10 000 payments: 1.33-1.37 MiB per snapshot (200 write+snapshot cycles: 42 -> 310-316 MiB). 30 000 payments: ~2.1 MiB per snapshot; after ~400 cycles of (correction + `GET /statement`) the container exits 139 (`FATAL ERROR: Ineffective mark-compacts near heap limit ... JavaScript heap out of memory`), all state lost. (A rejected correction between reads does not grow memory: 0.01 MiB.)
- Repro: `python3 attacks/snapshot_growth.py http://HOST:PORT 10000 200 <container>` (prints MiB per snapshot per mode; exit 1) and `python3 attacks/scale_snapshots.py http://HOST:PORT 30000 600 <container>` (crashes at ~cycle 400; output `run-scale-30k-docker.txt`). A history of 3 000 payments with ~2 000 write+read cycles costs about 0.8 GB, so the exposure is realistic only for heavy tests; but growth is linear and unbounded.

### S3-2 - Seeded hold with status `expired` and a future `expires_at`: historical view disagrees with the current view - Low
- Spec: `GET /me?as_of=T` describes holds as events; "Without as_of, use the instant the request began" (so `as_of=now` must equal the plain read); stage 2: only `open` seeded holds hold funds; stage 3: "seeded closed holds need not reconstruct a prior lifecycle".
- Actual: reset with `{"status":"expired","amount":300,"expires_at":"2099-01-01T00:00:00+00:00"}`: plain `/me` shows `held 0, available 10000`; `/me?as_of=<now-10µs>` and `?as_of=<now+1h>` show `held 300, available 9700` (the closed hold is treated as live until its future `expires_at`). Seeded `voided`/`captured` holds do not show this.
- Repro: `python3 attacks/seeded_expired_hold.py http://HOST:PORT` (exit 1, `run-seeded-expired-hold.txt`).

### S3-3 - RFC 3339 forms rejected: lowercase `t`/`z` and leap second - Low
- Spec: "`as_of` is optional and is an RFC 3339 instant with an offset" (same for `known_at`, `from`, `to`, correction `effective_at`). RFC 3339 §5.6 allows `t`/`z` in lower case and `60` in the seconds field.
- Actual: `2026-09-24T13:20:00z`, `2026-09-24t13:20:00Z` and `2026-09-24T23:59:60Z` are `422 validation_failed` on `/me?as_of`, `/me?known_at`, `/statement?from|to|known_at` and for correction `effective_at` (18 checks). Everything else behaved: `Z`, offsets up to `+23:59`, `-00:00`, 1 to 9 fraction digits (echoed exactly, compared at microsecond), `+24:00`, naive, bare date, empty, space-separated, `+0000`, `T24:00`, minute 60 -> 422; `year 0000` accepted.
- Repro: `curl -H "Authorization: Bearer $T" "$URL/me?as_of=2026-09-24T13:20:00z"`; `attack_s3.py ... D C`.

## Observations (not failures)
- Container clock vs host: the container's clock sat 1-2 ms behind the host in normal runs (so `effective_at` = host-now minus <2 ms can be rejected as "later than now"). In one fuzz run immediately after a container restart (seeds 200-201) the container clock was at least 17 ms ahead of the host and my oracle (which uses the host clock) logged 50 mismatches; the same seeds replayed twice afterwards produced 0 mismatches in 70 000 comparisons, so I attribute it to Docker VM clock adjustment, not to the service. I recorded the final clean run only.
- Statements for imported stage-2 state: stage-2 timestamps are millisecond-resolution, so a creation and a capture in the same millisecond collapse to one instant (handled consistently).
- `from > to` on `/statement` returns 200 with an empty window (builder-disclosed).
- Duplicated query parameter (`as_of` valid then invalid): the first value wins (200).
- Stage-1 and stage-2 observations unchanged (S2-1 silent failed refresh, S2-2 Accept q-values).
- The statement `snapshot` token does not survive `/_test/import` (404 afterwards); the spec only requires tokens until reset.

## What passed
### Oracle fuzz (`fuzz3.py`, `run-fuzz-docker-final.txt`: 93 758 comparisons, 0 failures)
Random sequences over 4 users + an operator with seeded timestamped history: payments, corrections (amount up/down/zero/same, `effective_at` in the past, before earlier payments, equal to other payments' instants and `±1 µs`, hold event instants, offsets and 0/3/6-digit fractions, stale revisions, wrong senders, capture and settlement payments), authorizations with 2-3 s TTL, final and nonfinal captures, voids, expiry, settlements, request payments. After every step: current `/me` of all users vs oracle; every 4th step: 12 random `/me?as_of&known_at` (instants at every event time `±1 µs`, `0`, far past/future, with/without each parameter, mixed offsets) and 8 random `/statement` windows (from/to/known_at/limit/offset): opening, closing, entries, `delta`, `balance_after`, `revision`, `effective_at`, `recorded_at`, `payment.amount`, `has_more`, ordering by `(effective_at, id)`, `opening + sum(delta) == closing`, running balance, snapshot token paging identical to the frozen full result after later activity; echo of `as_of`/`known_at` exactly as given; sum of totals == seeded total (current and historical); correction outcomes (201 / `insufficient_funds` / `historical_overdraft`) equal to the oracle's prediction in every case, failed corrections leave all views and the revision list unchanged and their key reusable; payments/authorize/settlement/request-pay refused only when the oracle says unaffordable; `closed_at` windows for void and clock expiry; after waiting out every short TTL all holds read 0.
