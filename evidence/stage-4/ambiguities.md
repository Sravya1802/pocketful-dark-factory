# Pocketful stage 4 — ambiguity notes

Dark run: no questions asked. `Strict` = the check fails an implementation that reads it differently; `Lenient` = either reading passes.
Stage 1–3 notes still apply to everything inherited. The model fuzz (FZ4) **skips** any operation whose simultaneous error conditions the spec does
not order, so only spec-pinned precedences are ever asserted by it.

| # | Question | Choice and reason | Strict / lenient | Checks |
|---|---|---|---|---|
| E-01 | Refund amount range. | "Invalid amount is 422": integer 1..1000000000. `0` is invalid (a refund of nothing is meaningless; payments also start at 1). Strings/booleans/fractions/missing/negative/over the maximum → 422; `null`/array/object: 400 or 422; integral forms (`100.0`, `1e2`) valid. | Strict (0, numbers) / Lenient (null, array) | RF-05 |
| E-02 | Order of refund checks. | 401 → 404 unknown → 403 non-receiver → 400 key → 400 body → claimed key resolved → 422 amount → … The remaining three (422 `invalid_refund_target`, 422 `refund_exceeds_payment`, 409 `insufficient_funds`) are asserted only one at a time; the fuzz skips any op where two of them hold at once. | Strict on the pinned pairs | RF-03 RF-04 RF-08 RF-06 RF-10 |
| E-03 | Refund by a non-receiver of a refund payment. | 403 (permission first). Only the receiver's attempt (422 `invalid_refund_target`) is asserted. | Strict | RF-08 |
| E-04 | Is a payment that settled a *request* refundable and correctable? | Yes: "direct payment, request payment or capture". Its request stays `paid` with the original `payment_id`. | Strict | RF-09 BC-12 |
| E-05 | "Refunds cumulatively may not exceed the payment's current corrected amount". | Σ refunds ≤ latest revision's amount (corrected). A correction may equal the refunded amount; one below → `refund_exceeds_payment`; a payment corrected to 0 admits no refund. | Strict | RF-06 RF-07 RF-14 |
| E-06 | Where does a correction below the refunded amount fall in the single-correction precedence? | After the permission check, validation, `linked_payment_immutable` and `stale_revision`; before funds and history. In batches it is an *item* error (reported in input position order). The fuzz only generates it alone. | Strict when alone | RF-07 BC-13 |
| E-07 | Fields of a refund payment. | `refund_of`=target id; sender/receiver swapped; `note`/`visibility` copied from the **original** payment (not from a later correction); `request_id`, `authorization_id` and `settlement_id` are null (a refund of a settlement member is not a member). | Strict (settlement_id: null or absent) | RF-01 RF-09 RF-20 |
| E-08 | Refund payment timestamps and revisions. | Ordinary new payment: `created_at` now; revision 1 with `effective_at = recorded_at = created_at`; immutable (`linked_payment_immutable` for its sender — 403 for anybody else). | Strict | RF-11 RF-12 |
| E-09 | Is the batch's authorization identical to settlements'? | Yes: no token 401; authenticated non-operator 403 (even the payments' own sender) **before** the body or key is examined; operator without key 400; key > 255 chars 422. | Strict | BC-01 |
| E-10 | Batch body shape. | `corrections` missing, not an array, empty, > 32, or containing non-objects/duplicate `payment_id`s → 422 `validation_failed` (shape errors are 422 even for wrong JSON types, as for settlements). Item fields of the wrong type: 400 **or** 422; item value errors: 422. | Strict (shape) / Lenient (item types) | BC-08 BC-10 |
| E-11 | Precedence inside ONE item. | Not asserted when two item-level errors coincide (unknown + invalid, stale + immutable, …); across items the first failing item in input order wins. Item-level errors = validation, 404, immutable, stale, refund floor. | Strict across items | BC-14 BC-15 |
| E-12 | Do settlement-completeness errors come before or after refund/immutable errors of *other* items? | After: "item errors in input order, settlement completeness, …". An incomplete settlement plus a stale/unknown/invalid item elsewhere reports the item error. | Strict | BC-15 |
| E-13 | Incomplete AND different instants at once. | Not asserted (the fuzz skips it). Alone: incomplete → `incomplete_settlement`; complete but different instants → `validation_failed`. | Strict alone | BC-06 |
| E-14 | "Identical effective instants (offset spellings may differ)". | Equality of the instant, to the microsecond: spellings `+00:00`, `+05:30`, `Z` of one instant pass; 1 µs apart fails. | Strict | BC-05 BC-06 |
| E-15 | Which wallets are checked for "resulting current available funds"? | Every wallet touched: for each, available now + net effect of all proposed revisions must be ≥ 0 (wallets with a net gain cannot fail). A decrease debits the receiver, an increase the sender, per item. | Strict | BC-17 |
| E-16 | Batch revision body. | Each revision: `payment_id`, `revision`, `amount`, `effective_at`, `recorded_at` (= batch `recorded_at`), `reason`, `correction_batch_id`. Single (stage-3) corrections carry no batch id (absent or null). `GET .../revisions` exposes `correction_batch_id` on batch revisions. | Strict (batch) / Lenient (single: absent or null) | BC-02 BC-03 BC-04 |
| E-17 | "recorded_at strictly later than the previous recorded_at of every member". | Strictly after every member's latest earlier `recorded_at`, including revision 1 (`created_at`) and earlier single corrections. | Strict | BC-04 BC-30 |
| E-18 | A no-op item (same amount and instant) inside a batch. | Never generated (the fuzz perturbs the amount); stage-3's lenient rule (D-13) applies if a service accepts it. | n/a | — |
| E-19 | Batch correction of a settlement member after a refund of that member. | Allowed if the new amount ≥ refunded amount; membership is unchanged by refunds so the batch is still "complete" with exactly the original members. | Strict | BC-13 IM4-10 |
| E-20 | Which operator may use the batch? | Any user in `settlement_operator_ids`; operators need not be a party to the payments. Key scope is per operator. | Strict | BC-01 BC-19 |
| E-21 | Snapshots after import. | A statement snapshot token minted before the export keeps paging the same frozen entries after import (same or another process), for exports of stage 3 and stage 4; tokens die on reset. Tokens minted AFTER the export are not asserted. The cross-process check needs `ALT_URL` (second stage-4 instance). Stage-1/2 exports contain no tokens. If a stage-3 export genuinely lacks tokens, IM4-30 states that explicitly. | Strict | IM4-01 IM4-02 IM4-30 |
| E-22 | Payment objects across stages. | Stage 4 adds `refund_of: null` to every payment; comparisons with older stages ignore that key (stage-2 `UPG-10`, which byte-compares, is skipped by `--include-previous`; IM4-10 replaces it). | Lenient | IM4-10..30 |
| E-23 | `/_test/import` of a stage-1/2/3 export: opening balances, ids and timestamps. | As in stage 3 (opening = current − net effect of all imported payments); `refund_of` absent in the old state means null. | Strict | IM4-10 IM4-20 IM4-30 |
| E-24 | Fuzz hold timing. | Captures are created with a final capture immediately after authorising and use the service's own `created_at`/`closed_at`; probes never sit on those instants. | n/a | FZ4-01..04 |
| E-25 | "Bounded memory (snapshots stay O(1))". | Not black-box observable; only retention and correctness are asserted. | n/a | — |
