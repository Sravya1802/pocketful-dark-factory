# Pocketful stage 2 - attack report (adversary)

Revision attacked: `92bbbf9a729a71eeed95934b8a72fdbda4ad297c` (`git archive` of `stage-2/`, product code untouched, not read).
Built with `DOCKER_BUILDKIT=0` and an empty `DOCKER_CONFIG`; two containers (A :18200, B :18201, `--cpus 2 --memory 2g`) for cross-process import, plus one `--network none` container (health 200). A stage-1 service (621342c, host node) supplied real stage-1 exports. UI attacks ran in Chromium via Playwright (harness venv) at 375, 320 and 1280 px.
Scripts and recorded output in `evidence/stage-2/attacks/`: `attack_s2_api.py` + `s2lib.py` (API, 227 checks, `run-api-docker.txt`), `ui_attack_s2.py` + `ui_lib.py` + `contrast.js` (UI, 341 checks, `run-ui-docker.txt`), `ui_probe.py`, `shots/` (screenshots). Not run: the shipped harness and analyst suites (those are the other seats'); builder's own results were not used.

## Verdict
**No spec failure found in the API: 227 of 227 checks pass.** In the UI 336 of 341 pass; the 5 that fail are two low-severity findings below (a silent failed refresh, and `Accept` q-values). The UI is presentation-ready in my judgement (details at the end).

## Findings (reproduced)

### S2-1 - A failed explicit Refresh is silent - Low (product quality)
- Spec (product direction): "Provide considered empty, loading and error states"; competing-clients section.
- Expected: when `wallet-refresh` cannot reach the server (or gets a 5xx), the user is told the numbers are stale.
- Actual: with `/me` and `/activity` aborted (or answered 500), clicking `wallet-refresh` changes nothing: the balance, feed and "Updated today at HH:MM" stay as they were and no message or alert appears (no `role=alert`/`aria-live` element). Initial-load failures are handled well ("We couldn't load your requests/holds/activity. Try again").
- Repro: `ui_attack_s2.py URL URL 12` (check "U12.server unreachable on refresh"), or the probe: open `/`, `page.route('**/*', abort fetch/xhr)`, click `wallet-refresh`.

### S2-2 - `Accept` negotiation ignores q-values on `/requests` and `/authorizations` - Low
- Spec: "Return the UI for `Accept: text/html`; API requests without that header receive JSON."
- Actual: any `Accept` that mentions `text/html` gets HTML, even when JSON is preferred: `Accept: application/json, text/html;q=0.5` and `Accept: text/html;q=0.1, application/json` return `text/html` on both routes. Browser default, `text/html`, `application/json`, `*/*` and no header all behave correctly.
- Repro: `curl -H 'Authorization: Bearer T' -H 'Accept: application/json, text/html;q=0.5' $URL/requests` -> HTML.

## Observations (not counted as failures)
- Seeded authorization with status `captured` and no `captured_amount` reports `captured_amount: 0` (the UI then shows "Captured 0.00 EUR" for a captured 3.00 hold); a seeded `captured_amount` is honoured. The spec fixture does not say which default is intended.
- Unchanged resubmission of the pay form sends the POST again with the **same** key and body (server replays 200): balance falls once, one feed item, no error, so the spec's observable requirement holds; the network does see a repeat request. Same for request, split and authorise forms.
- A handle typed as `Bob`/` BOB ` is trimmed but not lowercased, so the user gets "No one on Pocketful has that handle" (handles are lowercase). Leading `@` is stripped.
- Capture with a completely empty body (not `{}`) is `400 malformed_request`; `authorizations: null` in a fixture is 400.
- Split handles with an empty element (`bob,,cy`) are accepted (empty element ignored); amounts `15.` and `.5` are rejected, ` 15 ` is trimmed to 15.00, `+15` is rejected, `1e2`, `1,5`, `15,00`, `$15` are rejected without a request.
- Pay on a request lost after commit shows a distinct `request-uncertain` message (extra testid, good).
- `/favicon.ico` is 404; unknown browser pages return HTTP 404 with a page.
- Stage-1 observations unchanged.

## Attacks that passed (what I tried)

- **Capture/void/expiry (B, E):** 50 concurrent final captures with distinct keys: one 201, 49 x `authorization_not_open`, money once. 50 concurrent 100-unit non-final captures on a 1000 hold: exactly 10 succeed, cumulative 1000, closed, `payment_ids` 10 distinct, `payment_id` is the latest. Capture(600)/void race x15: never both, held 0, sums preserved. Void of a partially captured hold releases only the remainder and keeps the capture. Captures racing the 1 s TTL boundary: only 201 / `authorization_expired` / `authorization_not_open`, invariants hold. Expiry with no request at the deadline: after waiting past a 2 s TTL, `GET /me` shows the released `available`, `GET /authorizations` shows `expired`, `status=open` excludes it, `status=expired` includes it (receiver too), capture is `authorization_expired`, void is `authorization_not_open`; a partially captured hold that expires keeps its capture and releases only the remainder; creation replay after expiry returns the original body.
- **Available vs total (C):** payment/authorise/pay-request/settlement debit above `available` (but within `total`) -> 409 `insufficient_funds` and nothing moves; payment exactly equal to available works; settlement with zero net debit for a held wallet is affordable; void releases; capture spends reserved money while `available` is 0; 50 concurrent 900 holds on 10000 -> exactly 11 succeed; 2000 mixed authorise/pay/capture/void operations at 50 concurrency with 3 watchers reading `/me` continuously: at every read `balance == total`, `available == total - held >= 0`, `held <= total`; afterwards sum of totals == seeded total, held == sum of remaining of open outgoing holds, captured + remaining <= amount for every hold.

## Product quality (honest judgement)
Yes, presentation-ready. A consistent visual system (one type scale, rounded cards, one primary indigo, a dark-ink headline), a clear hierarchy where "Available to spend" is the largest figure and "Total balance" and "On hold" are small, with a one-line explanation of held money; `Held`, `Public`, `Waiting`, `Sent` and status chips are distinct; friendly copy ("@ada paid @bob", "Today at 04:43 PM"), technical ids hidden; the `/authorizations` screen is branded "Holds" with plain-language text ("Reserve money ... can't be spent until collected, released or expires") and both a human and the RFC 3339 expiry; sticky header navigation consistent across routes; 375 px layout is a single column with full-width controls, the desktop layout is two columns; uncertain states have their own message ("We couldn't confirm whether this payment went through. Press Pay again to retry safely"). Weaknesses: S2-1 (silent failed refresh), no lowercase normalisation of handles, and the seeded-captured display oddity.
